DHCP & DNS Troubleshooting: Addressing and Name Resolution

A structured first-response workflow for separating IP address assignment problems from DNS name-resolution faults in enterprise environments.

BY BIBEK CHAUDHARY　·　PRACTICAL TROUBLESHOOTING GUIDE　·　9 MIN READ

Scope and safety

Start with read-only checks and compare results against approved network documentation. Do not change DHCP scopes, reservations, DNS records, relay settings, VLANs or firewall rules without the responsible team's approval and an authorised change. Sanitise hostnames, IP addresses and command output before sharing publicly.

1. Define the symptom and blast radius

  • Establish whether the issue affects one endpoint, a group of devices, one VLAN, one site or multiple locations.
  • Record the affected device, switch port or wireless network, approximate start time, error message and business impact.
  • Compare a working device on the same subnet and, where permitted, a known-good device on another subnet.
  • Check for recent moves, changes, endpoint rebuilds, DHCP maintenance or DNS updates.

2. Check the endpoint's IP configuration

On Windows, use ipconfig /all to review the IPv4 address, subnet mask, default gateway, DHCP server, lease times and DNS servers.

  • An address in 169.254.0.0/16 usually indicates the endpoint did not obtain a DHCP lease.
  • A missing or unexpected default gateway can point to an incorrect scope option, VLAN or endpoint configuration.
  • An unexpected DNS server may explain why only name-based access fails.
  • Check for duplicate-IP warnings and compare the subnet details with the approved site record.

3. Isolate DHCP lease failures

Follow the DHCP path in order: endpoint → access port or wireless network → VLAN → DHCP relay/helper → DHCP server and scope.

  • Confirm the endpoint is connected to the expected access network and VLAN.
  • Ask the network team to verify relay/helper reachability and the correct server target.
  • Check scope utilisation, available addresses, exclusions, reservations and lease state.
  • Review server logs for discover/offer/request/acknowledgement failures, where access is authorised.
  • On Cisco platforms, authorised read-only checks may include show ip dhcp binding, show ip dhcp pool, show ip interface brief and show logging.
Common DHCP patterns

One device affected: check its NIC, cable/Wi-Fi, authentication and local configuration. One VLAN affected: investigate VLAN assignment, relay configuration and scope mapping. Many VLANs or sites affected: check DHCP service health, shared infrastructure, recent changes and provider dependencies.

4. Test DNS separately from connectivity

First confirm the endpoint has a valid IP address and can reach its expected gateway. Then test name resolution using the configured resolver.

  • nslookup hostname.example.internal checks the configured DNS resolver.
  • nslookup hostname.example.internal 10.0.0.10 queries a specified resolver; replace the example address with an approved internal resolver.
  • In PowerShell, Resolve-DnsName hostname.example.internal provides additional record and response detail.
  • Compare the response from a working endpoint and a second approved resolver if policy permits.
  • Check whether the failure concerns one record, one DNS zone, reverse lookup, conditional forwarding or all name resolution.

A successful connection to a service by IP address but not by hostname suggests a name-resolution path worth investigating. It does not, by itself, prove the DNS server is the root cause; application, routing and access controls may also be involved.

5. Interpret common DNS symptoms

  • NXDOMAIN: the queried name was not found in the responding DNS view; confirm spelling, suffix and authoritative zone.
  • Timeout: check resolver reachability, UDP/TCP 53 path, server health and firewall policy with the network team.
  • Intermittent or stale answer: review TTL, record lifecycle, replication and cache behaviour.
  • Internal name fails, public name works: investigate internal zones, VPN path, split DNS and conditional forwarders.
  • Only one application fails: validate the exact FQDN and service dependency rather than assuming a general DNS outage.

6. Be careful with endpoint refresh commands

Commands such as ipconfig /release, ipconfig /renew and ipconfig /flushdns can change local network state or interrupt a user's session. Use them only on an approved test device or with the user's agreement and according to the support runbook. Capture the original configuration and results first.

7. Build a useful escalation handover

Impact: affected users, devices, sites and business services

Addressing: sanitised IP/subnet, gateway, DHCP server and lease details

DNS: FQDN tested, resolver used, response code and timestamp

Checks: commands run, expected result and actual result

Context: recent changes, VLAN/site, wired or wireless path

Next action: team or owner required, dependency and update time
