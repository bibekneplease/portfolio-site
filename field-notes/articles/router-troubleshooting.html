Router Troubleshooting: Gateways, Routing & WAN

Diagnose gateway reachability, routing, DHCP, DNS, WAN and VPN symptoms while separating local, upstream and provider faults.

BY BIBEK CHAUDHARY　·　PRACTICAL TROUBLESHOOTING GUIDE

Scope and safety

This is a first-response learning guide. Follow the organisation's approved runbooks, access controls and change process. Use read-only diagnostics first. Do not alter production configuration, reload equipment, move live cabling or interrupt services without explicit authorisation and an approved change.

1. Establish where connectivity fails

  • Identify whether the impact is one device, one subnet, one site, a WAN circuit or multiple locations.
  • Compare wired, wireless and alternate-site symptoms where permitted.
  • Record source network, destination service, time, error message and business impact.

2. Check endpoint addressing and gateway

  • Confirm the device has an expected IP address, subnet mask, default gateway and DNS servers.
  • Check for an APIPA address, duplicate-IP warning or unexpected DHCP scope.
  • Use approved endpoint tools such as ipconfig /all, ping and tracert on Windows.

3. Validate routing and next hops

On Cisco IOS, authorised read-only checks can include show ip route, show ip interface brief, show interfaces and show logging. Confirm the expected route and next hop with the network design or operations team. A failed ping alone does not prove a route is absent; ICMP may be filtered.

4. Separate DNS, WAN and application symptoms

  • If an IP destination works but its hostname does not, investigate DNS resolution and approved resolver health.
  • If local resources work but external destinations fail, check WAN circuit status, edge interfaces and provider notifications.
  • If only one application fails, validate the application service and permitted ports before assuming a routing issue.
  • For packet loss or latency, compare multiple approved destinations and record time, path and test conditions.

5. VPN and remote connectivity

  • Confirm user/device identity, client status, authentication result and assigned address according to policy.
  • Check whether the issue affects one user, a group, one tunnel or all remote access.
  • Escalate tunnel negotiation, route advertisement, firewall policy and certificate issues to the authorised network/security team.
Safe troubleshooting boundary

Do not add static routes, alter ACLs, NAT, firewall rules, routing protocols or VPN settings as an ad-hoc fix. These are controlled changes requiring impact assessment, approval, rollback planning and change records.

6. Useful escalation evidence

Include source/destination (sanitised for public notes), timestamps, affected subnets or sites, endpoint addressing, DNS result, trace summary, interface status, circuit reference and recent changes.

Good incident records capture scope, impact, timestamps, device identifiers permitted by policy, evidence, checks performed, recent changes and the next owner. Remove passwords, secrets, public IPs and sensitive topology details from public notes.
